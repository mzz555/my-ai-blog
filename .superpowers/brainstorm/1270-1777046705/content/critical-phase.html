Critical 阶段设计

补全后端缺失接口，使菜单管理和角色管理页面从"404 报错"变为"完全可用"

一、菜单管理（MenuController）

需要新建的后端文件
MenuController.java — 4 个端点
MenuService.java — 接口（listTree / create / update / delete）
MenuServiceImpl.java — 实现
MenuMapper.java — BaseMapper<Menu>
dto/menu/MenuDTO.java — 请求体
API 端点
GET /api/admin/menus → 树状结构列表
POST /api/admin/menus → 新建菜单
PUT /api/admin/menus/{id} → 更新菜单
DELETE /api/admin/menus/{id} → 删除（含子菜单）
字段映射说明（前端 ↔ 后端差异）
前端字段 后端字段 转换规则
visible: boolean status: int true→1, false→0
sort: number sortOrder: int DTO 中直接映射
children: Menu[] @TableField(exist=false) Service 层递归组装
parentId: null|number parentId: Long 直接映射，顶级为 null
Menu 实体已有 children 的 @TableField(exist=false) 声明需补充， Service 层 listTree() 先查全部 menu，再在内存中递归组装父子关系，返回根节点列表。
删除操作需级联删除子菜单（SQL 已有外键，需设置 ON DELETE CASCADE 或 Service 层手动递归删除）。

二、角色管理（RoleController 补全）

补充的 API 端点
GET /api/admin/roles → 已存在 ✅
POST /api/admin/roles → 新建角色
PUT /api/admin/roles/{id} → 更新 + 重分配权限
DELETE /api/admin/roles/{id} → 删除角色
关键数据结构不匹配
前端期望：role.permissions = [{id, code}]
后端返回：role.menus = [Menu]

解决：新建 RoleVO，将 menus 映射为 permissions({id, code})， GET /api/admin/roles 改为返回 List<RoleVO>
请求/响应 DTO 设计
// 请求体 RoleDTO（POST/PUT）
{ name: String, description: String, permissionCodes: List<String> }

// 响应体 RoleVO（GET）
{ id, name, code, description, status, permissions: [{id, code}] }

// 权限分配逻辑
POST/PUT 时：先删 role_menus where role_id=?，再根据 permissionCodes 查 menu.code IN(...)，批量插入 role_menus
前端 allPermissions 硬编码了 6 个权限码： article:read, article:write, article:delete, comment:manage, user:manage, role:manage。 这些必须与数据库 menus 表中 BUTTON 类型记录的 code 字段一致（V2__seed_admin.sql 需核对）。

三、前端侧（菜单 + 角色视图）

两个视图的 UI 逻辑已基本完整（模板、表单、弹窗、CRUD 调用均已写好）， 后端接通后只需做以下调整：

MenuManageView 调整点
  • 响应数据中 sort ↔ sortOrder 字段名统一
  • visible ↔ status 布尔转换显示

  • 按 Pencil 设计稿调整样式（深色 #13131E 卡片背景）
RoleManageView 调整点

  • POST/PUT 发送 permissionCodes 数组（已实现）
  • 删除需检查角色是否被用户绑定（提示但允许删除）
  • 按 Pencil 样式统一权限 tag 颜色（#E8A838 amber）
